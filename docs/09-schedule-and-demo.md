## 최종 데모 성공 기준 (7항목 · `/demo-check` 스킬이 이 목록을 검사한다)

1. 하나의 기술문서를 업로드한다.
2. `고객 / 기술설명 / 5분 / 설득형`을 선택한다.
3. 5장 안팎의 발표자료가 생성된다.
4. **모든 슬라이드에 원문 근거가 하나 이상** 있다.
5. 스크립트와 예상 Q&A가 생성된다.
6. 검증 탭에서 최소 1건의 "주의" 또는 "확인됨" 결과가 **설명 가능하게** 나온다.
7. 같은 문서를 `신입사원`으로 바꾸면 **표현만이 아니라 구성이 달라진다** — 장수·슬라이드 순서·
   구성 전략(`slide_deck.strategy`)이 모두 달라야 통과한다. 용어와 설명 깊이만 달라지는 것은
   "프롬프트 옵션을 UI로 만든 것"과 구분되지 않으므로 통과로 치지 않는다.

## 3분 영상 시연 순서 (하이라이트는 "다시 설계"다)

심사자가 3분 뒤에 기억해야 하는 문장은 하나다 — **"얘네는 청중에 따라 다시 설계해준다."**
기능을 열거하지 말고 이 한 문장이 화면으로 증명되게 한다.

1. 기술문서 하나를 올린다. (조건은 `신입사원 / 기술설명 / 5분`)
2. "먼저 신입사원 대상으로 만들어 보겠습니다." → 배경부터 쌓인 6장이 나온다.
   맨 위 **`AI 구성 전략`** 카드를 소리 내어 읽는다.
3. **청중만 `임원`으로 바꾼다.** 원문도 목적도 시간도 그대로라는 점을 말한다.
   → 4장으로 줄고 결론이 맨 앞으로 온다. 구성 전략 문장도 함께 바뀐다.
4. **`청중 비교` 탭**에서 두 덱을 좌우로 세운다. 장수·순서·선택된 정보가 한 화면에 보인다.
5. 마지막으로 `정확성 검증` 탭에서 원문 근거를 연다.

3번과 4번이 하이라이트다. 설명보다 화면 전환이 강하므로 말을 줄인다.

## 평가표 대응 산출물 (발표 자료용)

- **AI 도구 선택 근거:** 문서 분석·자연어 재구성은 LLM / 원문 근거·숫자 검사는 규칙 검증 로직
- **산출물 품질 비교:** 같은 원문을 신입사원·임원·고객용으로 생성해 나란히 제시
- **원인 분석:** 기존 작업을 `자료 읽기 → 구조 작성 → PPT 작성 → 스크립트 → Q&A`로 분해해 각 시간 측정
- **데이터 기반 효과:** 최소 3회 테스트의 **중앙값**을 Before/After에 사용. 예시값과 실측값을 구분 표기
- **현업 적용 장치:** 모든 슬라이드에 원문 출처 표시, 고객용 결과에 내부정보 검토 경고
- **구현 가능성:** 이번 데모 구현 범위와 향후 메일·드라이브·사내 템플릿 연동 계획을 분리해 설명

측정 기록은 `docs/metrics/` 아래에 날짜별로 남기고, 추정치에는 반드시 `(예시값)`을 표기한다.
